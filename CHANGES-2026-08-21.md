## Vision changes (the short version)

1. **Every frame is now used.** Cameras shoot ~90 fps, robot loop is 50 Hz;
   we were throwing away roughly half our measurements.
2. **Soft limits replace hard walls.** Slightly-too-far or slightly-too-ambiguous
   measurements are now trusted *less* instead of being thrown away. Only truly
   bad data (>1.5x distance limit, ambiguity ≥ 0.5, or a >1 m "teleport") is dropped.
3. **Vision no longer steers heading from a single tag.** Single-tag frames only
   correct X/Y position (theta std dev = infinity). The NavX gyro owns rotation.
   Multi-tag frames still contribute heading.
4. **Startup logging** of the expected field layout and photonlib version.

### New Constants (VisionConstants)

| Constant | Value | Meaning |
|---|---|---|
| `kAmbiguityRejectLimit` | 0.5 | Ambiguity past this = drop the frame |
| `kAmbiguityMaxPenalty` | 6.0 | Worst grey-zone trust = 1/6 weight |
| `kDistanceRejectMultiplier` | 1.5 | Hard-drop only beyond 1.5x max range |
| `kSingleTagXYStdDev` | 0.35 m | Replaces old combined matrix |
| `kMultiTagXYStdDev` / `kMultiTagThetaStdDev` | 0.10 m / 0.15 rad | Replaces old combined matrix |

Old `kSingleTagStdDevs` / `kMultiTagStdDevs` matrices are gone — if any other
code referenced them it will fail to compile (grep shows nothing else did).

## ClimbCommandV2 (the short version)

Same phase plan V1 *documented*, actually implemented this time:
align → extend → **approach (the move that never ran in V1)** → climb.

Key improvements over V1:

- Trapezoid motion profile: plans accelerate/cruise/decelerate up front,
  arrives gently instead of overshooting (pattern from MA 6328's DriveToPose).
- Tolerance tightened 7 cm → 3 cm (~1.2"), heading 5° → 2°.
- Dwell check: must stay inside tolerance 0.1 s before declaring arrival.
- Per-phase watchdog timers with logged warnings (never freezes mid-sequence).
- Phase transitions logged — match logs read like a story.
- Proximity-sensor early-out during approach retained.

### Tuning knobs (all at the top of ClimbCommandV2.java)

| Knob | Default | Note |
|---|---|---|
| `kPositionToleranceMeters` | 0.03 | Tighten only after repeatability testing |
| `kHeadingToleranceDegrees` | 2.0 | |
| `kArrivalDwellSeconds` | 0.10 | Raise if arrival flickers on logs |
| `kDriveMaxVelocity` | 0.5 m/s | Speed up LAST, after accuracy proven |
| `kDriveMaxAcceleration` | 1.0 m/s² | Lower if wheels slip on start |
| `kDriveP/kDriveD`, `kThetaP/kThetaD` | 3.0/0.1 | Tune from logged error traces |

## How to test (in order!)

1. **Bench, no field:** deploy, open AdvantageScope, watch
   `ClimbCommandV2/*` keys. Run "Climb Command V2" from the dashboard with the
   robot on blocks. Confirm phases advance: ALIGNING → EXTENDING → APPROACHING
   → CLIMBING → FINISHED, and that warnings appear if watchdogs fire.
2. **Layout check first (REVIEW.md A1):** confirm both PhotonVision coprocessors
   show the SAME AprilTag layout as the new startup log line
   (`Vision/ExpectedFieldLayout`). This is still the #1 suspect for last
   season's flakiness — no code fix can paper over a layout mismatch.
3. **Static repeatability:** park at a marked spot, 30 s, read pose σ from the
   log. Target σ < 2.5 cm (REVIEW.md Phase B).
4. **Field, driver control:** run V2 from the dashboard against a real cage.
   Compare final placement vs V1 several times each.
5. **Only then** consider swapping autos' `"climber on"` named command to V2.

## Rollback

Everything is additive except the Vision rewrite. To roll back vision:
`git checkout main -- src/main/java/frc/robot/subsystems/Vision.java` and revert
the VisionConstants block in Constants.java. ClimbCommandV2 can be disabled by
deleting its two wiring spots in RobotContainer (marked `CHANGE (v2 rollout)`).
